# Changelog

Serra follows [Semantic Versioning](https://semver.org) once it reaches 1.0. Until then, any alpha may change the profile or state format; such changes are called out here.

## Unreleased

- **eve on Vercel:** a profile's agent can be an eve agent deployed on Vercel. Pick **eve** in **Add…** › **Profile**, or **Connect eve agent** in **Settings › Worker**, and enter its URL. One line says what leaves this Mac (requests, follow-ups, your answers and the knowledge index) and the button names the host: pressing it is your yes, and Serra checks the connection before saving. eve signs in with your own `vercel login`; a Deployment Protection bypass secret goes to the Keychain (or stays a 1Password reference) and only to eve's own process. Approvals and questions wait for you as with any agent, failures read "Sign in to Vercel…", "This deployment is protected…" or "Can't reach…", and the profile shows a small cloud mark. **Remove** deletes the Keychain item. See `docs/eve-cloud.md`.
- **Approvals follow you:** when an agent working on your own request asks to run a tool, the approval now also reaches you in your private chat with the bot on every other connected chat (Telegram, Discord, and your Slack DM once you've written to the bot there), with a small "From Slack · Open thread" line. Answer wherever you are: the first answer counts, and every copy (and the card in the job's thread) then says it's done, such as "Answered in Telegram", with no buttons left to press. A chat that was offline catches up when it's back. Only you can answer a copy; teammates' approvals and other questions stay in their thread. Nothing to set up, and with only Slack connected nothing changes. In Jobs, a waiting question now reads "Asked in chat".
- **Discord:** talk to your bot from Discord. **Settings › Channels** › Discord › **Connect**, paste your bot's token from the Developer Portal (kept in the Keychain, or a 1Password reference), **Add to server**, then DM the bot the code shown to make it yours. Mention it in a channel and it works in a thread; DM it for private jobs. Approval buttons, files and follow-ups work as in Slack, and Slack and Telegram keep working beside it. Outbound Gateway connection, so no open port and no server. Owner only for now. See `docs/discord.md`.
- **Telegram:** message your bot from your phone. **Settings › Channels** › **Connect**, paste the token @BotFather gives you (kept in the Keychain, or a 1Password reference), then **Open in Telegram** and tap Start to make it yours. Jobs, follow-ups, photos and approval buttons work there as in Slack; Slack keeps working beside it. Long polling, so no open port and no server. Owner only for now. See `docs/telegram.md`.
- **Linux:** the bot runs on a Linux machine without the app, as a systemd user service. `./scripts/install.sh` installs it from a checkout, adding Node 24 for you only (checksum-pinned) when it's missing, and a `serra` command; `serra server doctor` checks the machine. No sudo, no open port. See `docs/linux.md`.
- **Profiles:** run more than one bot from one app. Click the name at the top of the sidebar (or ⌘⇧N) and pick **Add…** to set up another bot with its own Slack app, knowledge, agent and settings. From the second one the top row shows the bot in use, and its menu, ⌘1…⌘9 and ⌘K switch between them without mixing anything. **Settings › Profiles** orders them, picks each one's colour, and removes one after saving a checked backup (tokens left out) and moving its folder to the Trash. With one bot, the app looks as before, and nothing in your profile folder changes.
- **All profiles live:** with two or more bots, the app follows every one at once. The switcher shows each bot's state as it changes, the menubar lists every bot with its state (open it, start a task, restart or stop it) and its icon shows the worst one, notifications name their bot (several within 10 seconds come as one, and a click opens that bot), and Jobs shows one quiet line when another bot needs you. Every bot now follows app updates, not only the one on screen. With one bot, the menubar and notifications read as before.
- **Pair with a server:** **Add…** now offers **Profile** or **Server**. On a Linux server, `serra server gateway --install` runs Serra's gateway (loopback and Tailscale only, TLS with a pinned certificate, no root, no open port) and `serra server pair` shows a code and three words; the Mac types the address and code, checks the words, and is paired. Or **Pair over SSH instead**, with your own keys. Codes work once, for 10 minutes, with 5 tries; each Mac's key stays in the Keychain, and `serra server devices revoke` cuts one off. The app lists the server's profiles; working with them from the app comes next. See `docs/linux.md`.
- **Servers at a glance:** once a server is paired, its profiles show in the switcher, the menubar and **Settings › Profiles** (a new **Where** column), each ending `· t480`, with the same dots and words as this Mac's. **Settings › Servers** lists each server as `up`, `offline` (after 15 seconds without an answer, every profile on it together, with **Retry**), `not paired` (with **Pair again**) or `update needed`; its page shows its profiles, one Diagnostics line, the Macs that can reach it (**Revoke** for the others) and **Forget**, which unpairs this Mac (revoking its key there first when it can) and deletes nothing on the server. A server's profile opens its server's page for now; opening it in the window comes with moves. With no server, nothing changes.
- **Move, restore and update:** a profile's page in **Settings › Profiles** now has **Move to t480…** (and **Move back to this Mac…** for a server's profile). Running jobs finish first, then the bot pauses, is backed up, copied and checked file by file, starts on the other computer, and only then leaves this one; knowledge, sessions, settings, held requests and channels go with it, and tokens go over the paired link into the other computer's own store (the Keychain here, the profile's `.env` on a server). Anything going wrong before it starts there puts it back as it was; a quit mid-move settles by itself when the app is back, and a server that loses its Mac starts the bot again after 10 minutes. The same page lists the profile's checked backups with **Restore…**, which saves today's copy first. A server's page shows its Serra version in Diagnostics and **Update t480** when it is older than the app: it checks out the app's release tag, restarts its gateway, and goes back by itself if the new version doesn't answer. Bots keep running through it.
- Fixed (move and restore): **Restore…** on a running profile always timed out and put today's copy back, because the restored bot was still held; once restored it also held new requests for half an hour. **Move back to this Mac** always failed when the profile's tokens went into the Keychain. If a move's last answer from the other computer is lost, the copy that started there is now stopped and set aside before this one runs again, so the bot never runs on both. A move or restore also waits for the app's own tasks on an ACP agent, and no new task starts while a profile is held.
- Fixed: **Check** on an eve agent that never answered (stuck installing or starting) could wait forever and leave its process running. It now gives up after a minute and ends the process.

## 0.1.0-alpha.9 (2026-11-28)

- Fixed: an ACP run whose agent stopped or lost its connection while an approval card waited (eve, which can't reopen a run) stayed **Working** forever. It now ends **Failed** with "… stopped while waiting for your approval", the card closes, and the tool never runs.
- Fixed: an ACP agent with no full-access mode, such as eve by URL without a `cwd`, ran every tool it asked for without a card. Each approval now waits for **Allow** in Slack or Jobs › Chat, whatever the agent's setup.
- **Knowledge conflicts, calmer:** a rule the bot learned again on a later day, with the day written in the line, is no longer a conflict. Dates, `(date, source)` notes, links and meeting tags are left out when lines are compared; real changes (a number, a day, a name, a "never") are still caught. Your pages aren't rewritten: old dated lines simply stop being flagged.
- **Needs you, calmer:** one quiet row per job, and far fewer words. Each pair of rules that disagree leads with what differs ("3 hours" vs "4 hours") and opens to **Compare**: two cards, one **Keep** each. Every repeated rule is in one **Repeated rules** row: **Keep newer for all** handles the safe ones (one backup per page, undoable), and only the rules that need a choice show, each saying why in a few words. **Keep both** stops listing a pair without touching the page. Overview's tiles drop the duplicate **To review** count.
- Fixed: **Keep** on one pair hid every other row for that page until Overview reloaded. The weekly review can now tidy part of a page, and the brief asks the bot to keep the learned date in `sources:` and reword a rule in place instead of adding it again.
- Fixed: **Keep older** (in Review or Compare) dated the newer rule's "Until" line before that rule was learned, such as "Until 2026-11-16" for a rule from 2026-11-17. It now uses today.
- **Knowledge › Graph** now uses the whole window: the map fills the space beside the sidebar, spreads its islands to the window's shape and refits when you resize it, instead of sitting in a box in the middle.

## 0.1.0-alpha.8 (2026-11-27)

- **Images in Jobs › Chat:** pictures a worker saves in its worktree, a QA run or a temp folder now show in the chat, as they do in Slack, even when the path has spaces. Attached images keep their own name.
- **Run an ACP agent in its own folder:** give a custom agent a `cwd` in `agent-backend.json` and it starts there and works there for every job, instead of in a worktree. Each approval waits for a person. Made for app-bound agents such as eve. See `docs/agent-backends.md`.
- Fixed: an ACP run whose turn failed (not signed in, a usage limit, the agent gone) showed as **Done**. It now shows as **Failed** with the reason and waits under **Needs you**. Codex's usage limit says so, instead of "stopped with an error".
- When an agent asks you a question and its answer field repeats the question, the question now shows once.

## 0.1.0-alpha.7 (2026-11-27)

- **Jobs › Chat:** a run opens as a chat, on ACP agents and T3. You see the request, the reply as it streams, tool calls folded into compact rows, permissions and how they were settled, and images in and out. Answer or follow up from the box at the bottom; T3 runs keep **Open in T3**. It replaces the Transcript window.
- **A calmer, high-end look:** new dark and light colours, 32px fields with a soft focus ring, one dropdown style everywhere, and disabled buttons that read as off. **Settings** is one sidebar entry (⌘,) with its own grouped menu (Esc goes back), and each settings page has one **Save** bar (⌘S) that says when changes apply.
- **Knowledge, redesigned:** Overview opens on four numbers and a grouped **Needs you** list; Pages, Proposals and About me are quicker to read. New **Graph** shows what your bot knows as a map.
- **Jobs and settings, redone:** Jobs rows lead with the task, a short status and only the links a job has. Worker picks the agent from cards, Repositories is one table, Secrets has a row per token, and rare settings sit under **Advanced**.
- **Setup, Diagnostics, Tools and ⌘K, tidied:** setup keeps Back and Continue in view and says where each Slack token is. Diagnostics lists failing checks first, each with a button to fix it, and shows home-folder paths as `~`.
- **Contrast and layout:** text reads at 4.5:1 or more on every screen in light and dark, field edges and to-do rings at 3:1, and no screen scrolls sideways at narrow widths.

## 0.1.0-alpha.6 (2026-11-26)

- **Agent backends.** T3 stays the default. Jobs, app tasks, the knowledge interview, meetings and the weekly review can now run on an ACP agent instead: Claude Code, Codex, OpenCode, Gemini CLI or your own. Pick it in Settings › Worker › **Agent backend**. See `docs/agent-backends.md`.
- **Custom ACP agents:** add your own with **Add ACP agent**, or in `agent-backend.json`. Thanks @JonRoosevelt (#40).
- An ACP agent's tool approvals go to the bot's owner only.
- **Knowledge › Overview** shows how your notes help: how many replies used them this week, and a short **To do** when something needs you.
- **Weekly knowledge review:** suggests fixes to your notes. Nothing changes until you approve.
- When two rules disagree, keep one with one click (with Undo). Pages can be retired and restored. Brief & policy moved to Settings.
- Fixed: Meetings **Test** said a source was missing when it was added after T3 started.

**Upgrading from alpha.5**

- Nothing to change: T3 stays the default.
- The first time Serra saves `state.json`, it keeps a copy as `state.json.backup-<time>`.
- Rolling back to alpha.5: T3 jobs carry on. ACP jobs are dropped; they're still in that backup.

## 0.1.0-alpha.5 (2026-11-24)

- Fixed: About me now renders a page's Markdown instead of showing it as raw lines — headings, bullets, tables, quotes, fenced code, bold, italics, `code` and links (only http and https open, outside the app), so a preview reads the way the brief carries it.
- Fixed: Settings › Meetings forgot a source's **Test** result as soon as you left the screen, so a source that passed showed "Not tested" again. Serra now keeps the last answer per source in `meeting-sources.json` in the profile, shows when it ran ("Tested 2 h ago") with a **Test again** button, and shows the source untested again after a week or once the T3 provider or model changes. ## 0.1.0-alpha.4 (2026-11-22)

- Meetings (off until you turn it on in Settings › Meetings): send a new DM to the bot starting with "remember this meeting", with a Granola or Google Meet transcript link, a transcript file or pasted text. Serra keeps only the decisions you approve in Proposals, on pages your team may read, never stores the transcript, lists action items in a digest, and Forget meeting removes everything a meeting added. Reading a link and picking out decisions each run as a T3 thread in Serra's own empty folder (a T3 project called "Serra meetings"), on the provider and model you use in T3, so it works with Claude, Codex, Cursor and T3's other providers. These runs aren't sandboxed: they have the same access as any T3 thread, and only Serra's brief asks them to change nothing, which is why capture is off by default. Settings › Meetings shows which T3 provider runs meetings, and **Test** on a source runs one short T3 run only when you press it. See `docs/meetings.md`.
- Meetings are more reliable. A Granola or Meet transcript is now the read tool's own result, taken from T3's record of the run, so quotes are checked against the real text; a transcript that was cut short is refused as too long instead of accepted. Extraction and Test run in T3's approval-required mode, and a run Serra gives up on (a timeout, or a stop for approval) is stopped in T3; for a link run, which T3 doesn't let Serra stop, you get its link. Files a run leaves in Serra's meetings folder are moved aside instead of blocking every later run. A decision that changes a rule already on the page is proposed as a replace, wherever the old line is, and approving it removes that line. Sending the same meeting twice gets a short reply instead of a second set of proposals.
- Settings › Tools now takes its provider list from T3: Cursor, Antigravity and the others appear when they're on, marked "Not supported yet" where Serra can't read their MCP setup.
- **State format:** `state.json` now saves each job's lifecycle as one `phase` (idle, following a run, or waiting in T3), so a job can no longer be saved as "not followed" with a run still counted as going (the SERRA-54 class of stuck "running" job). The first time the bot writes the file it keeps a copy as `state.json.backup-<time>`, and it keeps writing the old fields beside `phase`, so an older bot or app after a rollback reads the same jobs. A job waiting on you in T3 is now checked every poll, so it carries on within seconds of your answer. A run the worker starts on its own (following CI) now makes its job followed until it ends, so it shows as running, including before an update. A job with a question card open shows the question in Jobs, not "waiting in T3". A question card left open after T3 stopped waiting is closed when the bot starts.
- Every message carrying the worker's words (replies, status and progress lines, question cards, uploads, review requests, an error's detail in the owner's DM) is now checked against who can see its thread at the moment it is written, not only earlier in the poll. If that last check fails, the thread gets the usual "made private" or "couldn't confirm" notice instead. A question card closed this way shows the fixed "closed" text.
- When a request fails in your own DM, Serra now says why in one short sentence (for example "T3 Code isn't running. Open it, then try again.") instead of the raw error, which stays in the log and Jobs; elsewhere the thread gets a plain notice. A request held during an update is no longer lost if the bot crashes while starting it, and a crash right after a reply no longer posts it twice.
- The app may ask for a star on GitHub, with a small card that never blocks anything: only after a few finished jobs over two days, when nothing is running and you're idle, at most three times, and never again once you star or pick **Don't ask again**. Settings › Updates and ⌘K have a permanent **Star on GitHub** link.
- Setup is now its own full-window flow: a short welcome, then You & repo, Connect Slack, Confirm you and Install and start, with a step rail, focus on each step's heading and announcements for screen readers. It finds what already exists first: a profile made by `pnpm run setup` or an older app, tokens in `.env` or the Keychain (checked, not asked for again), the owner, and a service installed under launchd. It resumes at the first missing step, and with several profiles it asks which one. The profile form is kept if you quit halfway, and the install step waits until the bot actually answers.
- Until setup is done, the sidebar has a **Finish setup** row with the steps left, and every screen that needs a profile shows the same calm **Finish setup** state instead of an error. Setup is also under **Serra › Set Up Serra…** in the menu bar and in ⌘K.
- Fixed: an update download that stalls now stops after a minute without any data and says so, with **Try again**, instead of staying on "Downloading…" until you cancel. A slow download that keeps receiving data is never cut off.
- ⌘K now opens with a screen selected, not **Restart bot**, so ⌘K then ↩ never restarts the bot; Restart bot is listed last.
- A person card without a `# Name` heading is now named after its file in About me instead of being left out.
- Connect Slack: when Slack refuses the tokens, the Slack-app card says so instead of "Your app's tokens are here." Meetings has its own sidebar icon, the welcome screen names any T3 Code provider, and the worker's brief no longer names one provider's question tool.
- A token check that never reached Slack (offline, a timeout) now says "Couldn't reach Slack" instead of "Slack rejected", on Secrets as well as in setup.
- Fixed: opening Serra with the bot token in 1Password asked for 1Password approval on every launch. The app no longer reads the bot token to show Slack names in Jobs: the running bot names the IDs and the app keeps the names in the profile (`slack-names.json`, names only). New names need the bot running on this version; the bot's own 1Password prompt when it starts is unchanged.
- Fixed: Jobs listed Slack threads as running when T3 wasn't running them. A run that started and finished between two of the bot's checks left a stale "seen run" behind, and state carried over from an older install could keep 👀, loading or a progress line forever. The bot now forgets a seen run once a later reply is posted, checks every job saved as running against T3 when it starts (clearing the 👀, loading status and progress line of threads T3 isn't running, and following the ones it is), and the Jobs list asks T3 before showing a Slack job as running.
- Upgrading from alpha.2: an **Update source** left over that can't work (the folder is gone, or it isn't Serra's code) is cleared shortly after launch, after backing up `profile.json`, so the bot follows the app; Updates says so in one line. Developer mode has **Follow app updates** to leave it the same way.
- Updates no longer says new requests wait while a bot from before alpha.3 (which doesn't hold them) finishes its jobs. GitHub release notes now end with how to upgrade from alpha.2 or older.
- Docs: the README now starts from the released app (download, checksum, install, first run), says how updates work and what a reinstall keeps, and how to migrate from a checkout-run Serra or another self-hosted bot. Running from source moved to CONTRIBUTING.

## 0.1.0-alpha.3 (2026-11-21)

**Upgrading from alpha.2:** install this one by hand, one last time. Download `Serra-0.1.0-alpha.3-arm64.dmg` below, quit Serra, drag the new Serra to Applications and replace the old copy. From alpha.3 on, Serra updates itself: Settings › Updates finds new releases, and **Restart to update** installs them. After you open alpha.3, the bot moves to the new version on its own once no job is running.

- Updates in the app follow GitHub Releases: it checks for a newer version (pre-releases included while you're on an alpha), shows the release notes, downloads and verifies it against the release's `SHA256SUMS`, and **Restart to update** replaces the app and opens it again (or opens the installer when it can't replace itself). The bot then moves to the new version on its own when no job is running. The commit-based flow is now a developer mode, shown only when Settings › Worker › Developer: update from a checkout is set, with clearer names (Build from checkout, Restart bot on it, Undo last switch). Bot builds record the app version, so the screen shows `0.1.0-alpha.3` instead of a timestamp.
- Updating the bot no longer waits indefinitely for a quiet moment: from **Restart to update** (or when the bot is found behind the app), new requests are held with an hourglass until the bot has restarted, while running jobs finish. Held requests start on the restarted bot. The pause lapses on its own after 30 minutes, so the bot never stays deaf.
- Fixed: Roll back on Updates (and `pnpm bot rollback`) right after setup stopped the bot and removed its service, with nothing to go back to. It is now off until there is an earlier bot.
- Old bot builds in the profile's `releases/` folder are removed after each switch, keeping the current one and the one before it.
- The app is still ad-hoc signed and not notarized: macOS asks once (System Settings › Privacy & Security › Open Anyway). Only an Apple silicon build is published; signing and a universal build are planned for the beta.

## 0.1.0-alpha.2 (2026-11-21)

First public alpha, for trying Serra locally on macOS. Serra bridges a chat app to your local coding agents; this alpha supports one chat channel, Slack.

- Slack channel: mentions and DMs become T3 Code threads in fresh Git worktrees; replies, clarifying questions (with buttons), images and files go back to the Slack thread.
- Private per-bot profiles outside the checkout: settings, tokens (`.env`, Keychain or 1Password), brief and policy, knowledge, state and logs.
- `pnpm run setup` and `./scripts/install.sh` for a new bot; `pnpm run doctor` to check the configuration, T3, GitHub and Slack.
- Background service under launchd with prepare, activate, status, restart and rollback.
- Knowledge interview and a proposals queue for teaching the bot how you work.
- Knowledge › About me: every job's brief carries what you've confirmed about yourself (your `owner/` pages and a one-line roster of `people/`), capped at 4,000 characters, for the audience that will see the reply. Pages say who may hear them with `audience: owner | team | external`; **a page without it is now yours only**, so teammates' briefs leave it out until you share it: About me lists such pages and shares the ones you pick in one step, and Pages has a picker on each page. Off-limits pages come first in About me and are never cut for size (1,500 characters for all of them); outsiders' replies carry a fixed rule that names no internal topic, and teammates' replies one too when your off-limits page is yours only. Each worker reads a snapshot of the pages its audience may hear, and Serra checks who can see a thread right before posting anything the worker wrote: a page taken back since, or a thread Slack can't describe, holds the reply. **After upgrading, a thread already running in a channel or a teammate's DM carries on in a fresh session on its next message, and a reply it finishes is held:** Serra doesn't know which pages it read. The interview asks about people, voice (optional samples) and off-limits topics, and records an audience for each page.
- Knowledge approvals are app-only and bound to what you reviewed: `pnpm bot proposals` lists and shows, workers are told never to promote, and a file edited outside Serra isn't used until you review its diff and accept or restore it in Pages. Merge replaces a page instead of appending, and an approval is refused when the proposal or the page changed since you saw it, or when it would write over a file changed outside Serra. The owner's first message in a thread is marked as the owner's. Existing profiles get the updated brief as a proposal in Brief & policy.
- Knowledge evals: deterministic safety tests in CI and a live, graded knows-you eval on an invented owner (`evals/`).
- Automatic investigations of messages in configured alert channels.
- `updates` in profile.json (Settings › Worker › Update source): the Serra checkout and branch that Updates counts new commits in and Prepare copies from, so a packaged app can follow the repository.
- macOS menubar app: the `.dmg` is attached to this GitHub Release (ad-hoc signed, not notarized: allow it once under System Settings › Privacy & Security › Open Anyway), or build it with `pnpm app:package`. It has a first-run wizard, Jobs, Knowledge, Brief and policy, Settings, Secrets, Tools, Updates and Diagnostics.
- Tools (app and `pnpm bot tools`), read-only: each provider's MCP servers from `claude mcp list` and `codex mcp list` (claude.ai connectors and plugins included, with their status), the command-line tools on your Mac (installed, version, signed in), and recommended services with commands to copy. A comment after `enabled = false` in Codex's config no longer reads as on.
- Releases are cut in CI: a release PR raises the version and dates this changelog, and merging it tags the commit and publishes a GitHub Release with the app (docs/releasing.md). CI also builds the app on every PR.
